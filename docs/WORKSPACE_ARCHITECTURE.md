# RPV Control System: рабочий цикл и архитектура

## Проблема и выбранное направление

Офису нужны ответы на три вопроса: что делать сейчас, где находится объект и что мешает закрыть заказ. Ранее одинаковые задачи были распределены между «Сьогодні», «Головна», «Проблеми» и другими экранами; объекты находились внутри списка менеджеров. Поиск передавал ID результата, но верхний компонент его отбрасывал. Карточки заявки отличались в разных разделах.

Цель изменения — уменьшить число переходов между заявкой, исполнителем, паспортом и документом. Рост бизнеса зависит от повторных заказов, качества исполнения и экономики рейса; оформление само по себе этих результатов не гарантирует.

## Что реализовано

- Один основной обзор: назначить исполнителя → выполнить → проверить результат → рассчитаться. Одна заявка получает одну следующую задачу. Проблема и просроченный срок повышают приоритет; выполненные и отменённые работы не возвращаются в оперативную очередь.
- Один источник навигации для компьютера и телефона. Внизу телефона постоянно доступны обзор, заявки, объекты и исполнители. Документы, расчёты и управление сгруппированы отдельно.
- Реестр объектов доступен напрямую. Выбор сети ведёт к списку АЗК, паспорт показывает связанные заявки по customer_site_id. Совпадение номера АЗК само по себе не связывает записи разных сетей.
- Единый центр действий заявки из обзора, списка, паспорта и поиска. Сохраняются назначение, сроки, проблемы, комментарии, фото и история; отдельная вкладка показывает описание, объём и выплату. Акт и паспорт доступны непосредственно из карточки.
- Страница и открытая запись отражаются в URL. Перезагрузка восстанавливает контекст; Back/Forward работают через popstate. Поиск открывает найденную заявку, акт или исполнителя.
- Статус «ожидаем акт» отделён от отправленного на проверку акта. Очередь использует последний акт; старый отклонённый акт не заслоняет новое исправление.
- Приоритетный список не обрезается незаметно до 20 записей: есть «показать ещё». Заявки и состояние актов читаются страницами, чтобы стандартный лимит ответа не скрывал записи.
- На обзоре не вычисляются выручка и прибыль из выплаты подрядчику. Показана только сумма ожидающих выплат за принятые работы. Нулевая выплата не создаёт задачу расчёта.
- Синие и голубые поверхности и состояния; оранжевый отмечает требующую реакции работу. Контрастные подписи, доступное увеличение масштаба, адаптация к reduced-motion.
- Старые независимые CSS-надстройки мобильных экранов больше не подключаются. Общие стили нового пространства находятся в workspace.css.

## Разделение ответственности

| Слой | Ответственность | Источник |
|---|---|---|
| Навигация | Разделы, URL и открытая запись | src/workspace/navigation.ts |
| Оперативная модель | Следующая задача и её приоритет; без изменения статусов | src/workspace/workflow.ts |
| Загрузка обзора | Полный набор заявок и состояний актов | src/workspace/operationsApi.ts |
| Карточка заявки | Один компонент действий, связанный паспорт и документы | ApplicationWorkspace + ApplicationActionDrawer |
| Паспорт | Связанные заявки по ID объекта | ObjectProfile + office.site |
| Сервер | Проверка активной офисной роли, существующие транзакции исполнения и приёмки | rpv-portal / SQL functions |
| Telegram | Регистрация и действия участников | Текущий smart-api, этим выпуском не заменяется |

Дополнен только серверный read endpoint office.site. Он использует ту же проверку активной офисной роли, что office.sites, и валидирует UUID. Новых таблиц, выдачи прав и автоматического объединения объектов нет. Накопленные данные, финансовые подтверждения и Telegram-уведомления при выпуске не изменяются.

## Что показал разбор и что остаётся следующим этапом

| Приоритет | Разрыв | Следующее изменение | Критерий результата |
|---|---|---|---|
| 1 | Финансовые данные описывают выплату исполнителю, но не полный результат заказа | Договор и версия тарифа заказчика, цена исполнителя, минимальный заказ, налоговый режим, дополнительные затраты | У каждого принятого заказа проверяемая выручка, себестоимость и маржа; отсутствие тарифа явно видно |
| 1 | Ручное создание и назначение остаются старым сценарием; сбой уведомления после создания может выглядеть как полный отказ | Серверная идемпотентная команда создания с обязательным выбором объекта для сетевых заказов; отдельный статус доставки | Повтор нажатия не создаёт второй заказ, недоставка не отменяет успешно созданную заявку |
| 1 | Реестр допускает повторные паспорта и объекты без текущего закрепления | Очередь проверки дублей по сети + региону + коду + адресу; подтверждаемое объединение с журналом | История и доступы сохраняются, совпадающий код другой сети не объединяется |
| 1 | Отдельные части бота и репозитория имеют разную историю выпуска | Сверить текущий код развёрнутых функций с репозиторием; фиксировать версию релиза перед следующим обновлением бота | Бот воспроизводимо собирается из конкретного commit без отката живых исправлений |
| 2 | Плановая дата не равна гарантированному приезду; периодичность ещё не полноценный договорный график | Повторные обслуживания и подтверждение окна приезда, переносы с причиной | Менеджер и исполнитель видят одну согласованную дату |
| 2 | Один заказ пока не описывает несколько рейсов и частичное выполнение | Отдельные рейсы, фактические объёмы, фото и документы утилизации; итог заказа считается из принятых рейсов | Повтор акта не увеличивает объём; сумма рейсов проверяема |
| 2 | Резервное обновление каждые 15 секунд перечитывает списки | Серверные счётчики и курсор очереди; обновления изменившихся записей | Время открытия и объём передачи не растут пропорционально всему архиву |
| 3 | Уведомление не всегда равно подтверждённой доставке | Outbox с повторами, сроками реакции и эскалацией ответственному | Видно, кто должен отреагировать, когда и доставлено ли сообщение |

## Модель развития для ниши РПВ

Сеть → объект → условия обслуживания → заявка → назначение → рейсы и результат → приёмка → документы заказчику → оплата заказчика и выплата исполнителю.

Объём септика — характеристика объекта, фактически вывезенный объём — характеристика рейса, оплачиваемый объём — договорное правило. Их нельзя автоматически приравнивать. Аналогично работа исполнителя, одобрение акта и движение денег — разные события. Объект должен оставаться общим для всех трёх кабинетов, с доступом согласно роли.

Для оценки эффекта собирать: время от заявки до принятия исполнителем, долю работ в согласованный срок, длительность проверки акта, повторные выезды, маржу по заказу/сети и срок поступления оплаты. Сначала измерить базовый уровень; не заявлять процент улучшения без наблюдений.

## Проверка и выпуск

Автотесты охватывают приоритеты, отсутствие дублей задач, финальные состояния, последний акт, ожидание акта, границу суток по Киеву и URL. Сохраняются существующие тесты доступа, создания заявок, календаря и транзакций приёмки.

Браузерная проверка использует только явно синтетические заявки и контакты: desktop, телефон 390 px, сеть/объект/паспорт/заявка, Back, перезагрузка, поиск, прямое открытие акта и фильтр выплаты. Это не заменяет реальный выезд с телефоном исполнителя. Тестовые точки входа не входят в production build.

Порядок: опубликовать rpv-portal с новым read endpoint, затем собрать и выпустить web. Откат web возвращает предыдущую версию интерфейса; дополнительный read endpoint обратно совместим. Рабочий smart-api не развёртывать из устаревшего локального исходника.
