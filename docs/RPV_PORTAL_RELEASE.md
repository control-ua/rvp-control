# RPV Control — первый выпуск рабочих кабинетов

Статус: первый выпуск развёрнут после явного подтверждения владельца.

- Миграция `rpv_portal_access_and_links` применена к рабочей базе.
- `rpv-portal` v1 и `smart-api` v120 активны.
- PR #7 слит в main: `bfb22f31384633b13b2afd45b99dcce2682b700e`.
- GitHub Pages build и deploy завершились успешно: workflow run `42917489017`.
- Адрес: https://control-ua.github.io/rvp-control/. В боте доступны `/web` и кнопка «🌐 Відкрити вебкабінет».
- Проверено на рабочем сервере: 8 restrictive-политик, закрытые анонимные RPC, серверный доступ к переходам, отсутствие заявок для anon и сохранение доступа активного офиса. API отвечает 401 без входа/при поддельном Telegram-входе и 403 для чужого Origin.
- Проверено: smart-api отвечает 200 на health и отклоняет неподписанный webhook с 401.
- В браузере проверены опубликованный экран входа замовника и офисный логин. Полный вход из Telegram на телефоне и проверка двух разных реальных профилей ещё требуют пилота.

## Что готово

- Голубо-синий кабинет замовника `?cabinet=customer`: подписанный Telegram-вход, АЗК по публичным кодам, паспорта, месячные акты, защищённое скачивание основного файла акта, общий счётчик и помесячный архив. Поиск фильтрует текущую страницу объектов; предусмотрена пагинация.
- Заказчик видит текущие заявки только после явной привязки офиса к паспорту. Старые строки не сопоставляются автоматически. Загрузка паспортов продолжается через действующий бот.
- Кабинет подрядчика `?cabinet=contractor`: только свои заявки, принять, отказаться от предложения и зафиксировать выезд. Проверяются активный профиль, назначение, этап и версия записи. Сдача документов остаётся в действующем боте.
- Раздел «Замовники» в существующей админке: подтверждение/отклонение контакта, сброс регистрации, телефон и Telegram, поиск сети/АЗК, явная привязка заявки и публикация уже подтверждённого акта. Сохраняется текущий вход офиса Supabase Auth. Назначение подрядчика и проверка актов используют существующие разделы админки.
- Публикация использует существующий `rpv_customer_publish` с проверкой совпадения адреса и защитой от повторного учёта. Уведомления используют тот же ключ `rpv_customer_delivery`, что и бот. Ошибки доставки показываются отдельно от результата записи.
- Кнопка «🌐 Відкрити вебкабінет» и команда `/web` в боте. Inline Web App кнопки выдаются только активным подтверждённым ролям, после проверки подписанного Telegram webhook.
- Все запросы проверяют актуальный доступ. Сервер проверяет подпись initData и срок до 1 часа. При истечении пользователь повторно открывает Mini App. Отдельной долговременной веб-сессии и входа Telegram OIDC в этом выпуске нет.

## Конкретные изменения рабочей базы

1. Nullable FK `applications.customer_site_id` → `rpv_customer_sites.id` и частичный индекс. Все существующие значения остаются NULL.
2. Закрытый журнал `rpv_portal_events`, доступный только серверному service_role, и две служебные RPC `rpv_portal_contractor_transition` / `rpv_portal_link_application`. RPC исполняются как invoker, используют блокировку строк, проверяют профиль/роль/назначение/версию и фиксируют событие в одной транзакции.
3. Дополнительная restrictive RLS-политика на `applications`, `contractors`, `acts`, `act_files`, `application_files`, `application_comments`, `automation_rules`, `notifications`: прямые запросы требуют активной офисной записи `admin_users`. Текущие permissive-политики остаются; новые права на операции не добавляются. Серверный бот продолжает работать через service_role.
4. У legacy SECURITY DEFINER RPC `claim_order` и `delete_act_and_application` отзывается EXECUTE у PUBLIC/anon/authenticated; серверному service_role доступ сохраняется. Поиск по текущему коду админки не выявил прямых вызовов этих RPC. Возможные сторонние потребители требуют проверки при пилоте.

Сброс регистрации использует существующую атомарную RPC и сохраняет паспорта, заявки и акты. Новая регистрация не возвращает прежние права автоматически.

## Границы выпуска и оставшиеся этапы

Веб-создание заявок заказчиком, веб-загрузка документов подрядчиком, OIDC-вход вне Telegram, собственный домен, унификация всех старых мутаций бота и веба и полный security-аудит legacy функций/файлового прокси остаются следующими этапами. Уже обнаруженный legacy `telegram-file` принимает file_id без собственной проверки владельца, поэтому новые кабинеты его не используют. Новая выдача актов проверяет доступ на сервере и возвращает байты без раскрытия URL с токеном бота. Полное закрытие legacy-прокси требует перевода существующих офисных img/link на авторизованное скачивание.

Для отката веба — предыдущий коммит Pages. Для остановки новой точки входа — вернуть smart-api v119 из сохранённого исходника. Миграция не удаляет рабочие записи. Не удалять поле привязки/журнал и не возвращать публичные права автоматически при откате интерфейса.
